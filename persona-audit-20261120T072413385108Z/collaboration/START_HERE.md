## 한 번의 협업 주기

1. Codex가 좁은 변경을 구현한다. 예: 환자 사실 보존, 정보 공개, 발화 스타일 가운데 한 문제.
2. Codex가 `review_request.md`에 목적, 실제 변경 내용, 원문 예시 2~4개, 확인한 결과와 남은 질문을 적는다. 제안·구현·실제 관측을 구분한다.
3. Claude는 이 작은 묶음만 읽고 중대한 문제·근거·수정안·다음 확인 실험을 제시한다. 전체 채팅이나 최종 성능 비교 자료를 읽히지 않는다.
4. Codex가 지적마다 채택/보류/반박과 근거를 기록하고 필요한 구현을 수정한다. Claude의 말도 오류 가능성이 있으므로 무조건 수용하지 않는다.
5. 단계당 검토는 우선 1회, 중대한 수정 후 추가 1회까지다. 새 증거 없이 서로 동의할 때까지 토론하지 않는다.

자료는 요청 파일과 응답 파일로 교환한다. 다른 앱의 대화를 자동으로 서로 읽는다고 가정하지 않는다. 한 번에 두 에이전트가 같은 구현 파일을 고치지 않는다.

새 개발 채팅은 먼저 이 인계문과 연결 결과를 읽고, `review_once.py`의 호출 없는 준비 확인을 실행한다. 그 다음 `review_request.md`에 준비된 M0 설계 검토를 Claude에 1회 요청하고, 응답의 수용·보류·반박 근거를 기록한 뒤 최소 발화 모듈을 구현한다. 연결 확인 문구를 받은 것과 임상·설계 검토가 수행된 것은 구분한다.
